## Item 1 — JIT Context Injection

### Problem
The current CHAT-ENTRYPOINT.md is 1075 lines and tells the LLM to read
constitution + router + workflow + 3-4 skills + schemas upfront. This
triggers "Lost in the Middle" — the model drowns in rules it doesn't
need for the current state.

### Design
A `ContextRouter` that, given `(workflowName, currentState)`, returns
a **minimal context bundle** containing only:
1. The current state's `purpose` text (from `.sm.yaml` `state_detail`)
2. The current state's `emits_evidence` kinds + their schema field lists
3. The current state's `safety_gate` declaration (if any)
4. Only the skills listed in the workflow's `skills_required` that are
   relevant to THIS state (filtered by the state's `purpose` text mentions)
5. The question budget for this state (if it's in `allowed_states`)

### File layout
- `executor/src/context-router.ts` — the router
- `executor/src/context-bundles/<workflow>-<state>.json` — pre-computed bundles (generated by a build script, not hand-authored)
- `scripts/generate-context-bundles.mjs` — build script that reads all
  `.sm.yaml` + `skills/*/SKILL.md` and emits the bundle JSONs
- `executor/examples/e2e-context-router/drive-run.mjs` — regression test

### What changes for the chat LLM
CHAT-ENTRYPOINT.md gets a new section: "Instead of reading everything
upfront, after each `aiecp:advance`, ask the user (or your tool) for
the context bundle for the new state. The bundle is ~200 lines, not 5000."

### Token savings estimate
- Current upfront load: ~5000 lines (constitution 200 + router 80 +
  workflow 200 + 4 skills × 400 + schemas 8 × 50 + memory schemas 4 × 30)
- Per-state bundle: ~200 lines (state purpose 20 + evidence fields 30 +
  relevant skill slice 100 + safety gate 10 + question budget 5)
- Savings: ~96% per state transition; pro-LLM's %60 estimate is conservative

## Item 2 — Tree-sitter + Universal AST Detector

### Problem
`discovery/cli/src/detectors/` has only `python.ts` and `typescript.ts`.
Go, Rust, Java, C++ projects get no symbol maps, call hierarchies, or
dependency graphs.

### Design
Add `universal-ast.ts` that uses `web-tree-sitter` (WASM-based, zero
native deps — keeps ADR-0022's "zero runtime deps" intact by vendoring
the WASM binary into `discovery/cli/vendor/`).

### What it produces
For any language Tree-sitter has a grammar for, the detector emits:
- `symbols`: list of `{name, kind, file, line, endLine}` (functions, classes, methods)
- `call_graph`: list of `{caller, callee, file, line}` edges
- `imports`: list of `{file, module, isLocal}`
- `complexity_hotspots`: top-N functions by cyclomatic complexity (proxy)

### Language coverage (Phase 1)
Start with grammars already on npm: `javascript`, `typescript`, `python`,
`go`, `rust`, `java`, `cpp`, `c`. JSON manifest in
`discovery/cli/src/detectors/tree-sitter-grammars.json` lists which
grammar WASM file to load per file extension.

### File layout
- `discovery/cli/src/detectors/universal-ast.ts` — the detector
- `discovery/cli/vendor/web-tree-sitter.wasm` — vendored WASM binary (~1.5MB, committed per ADR-0021 exception)
- `discovery/cli/vendor/grammars/*.wasm` — language grammars (~200KB each, 8 languages)
- `discovery/cli/src/detectors/tree-sitter-grammars.json` — manifest
- `executor/examples/e2e-universal-ast/drive-run.mjs` — regression test (parses a tiny Go + Rust sample)

### ADR-0022 compliance
ADR-0022 says discovery/cli has ZERO runtime npm dependencies. We
honor this by VENDORING the WASM binary + grammars (not `npm install`-ing
them). The `web-tree-sitter` npm package is dev-only (build-time type
shims); runtime loads `web-tree-sitter.wasm` via `fs.readFileSync`.

## Item 3 — OS-Level Sandbox (Docker/MicroVM)

### Problem
`safety-gate.ts` is prompt-level — it asks the LLM to confirm, but
cannot actually prevent a malicious `rm -rf /` if the LLM emits it.

### Why NOT WASI
Research (2026-08-16): `vm2` (the most popular JS sandbox) has
CVE-2026-26956 — a WebAssembly-based sandbox escape. `node:wasi` is
also exploitable (absolute-path file access). **WASI is not safe for
adversarial code.**

### Design — Docker-based sandbox
- `executor/src/sandbox-runner.ts` — runs commands in a Docker container
- `sandbox/Dockerfile.aiecp-executor` — minimal image (node:20-alpine +
  python3 + git; no network; `--read-only` rootfs; `--cap-drop=ALL`)
- `sandbox/run-in-sandbox.mjs` — wrapper script that mounts the project
  dir as read-only, runs the command, captures stdout/stderr/exitCode,
  then destroys the container

### Realistic scope — ADR only this phase
Real Docker integration requires:
1. Docker daemon available at runtime (CI yes, user laptop maybe)
2. Image build pipeline (registry or local)
3. Volume mount strategy that works on macOS/Linux/Windows
4. Timeout + OOM-kill handling

This is Phase 3+ work. **This phase: ADR-0030 records the decision +
a stub `sandbox-runner.ts` that throws "Docker not available — see
ADR-0030" until Phase 3.** No fake implementation.

## Item 4 — SWE-bench Integration

### Problem
`evaluations/scenarios/` has 25 synthetic scenarios. Pro-LLM's point:
"AIECP applied → regression errors %X decreased, first-try success %Y
increased" — needs SWE-bench to prove.

### Design — adapter, not a fork
SWE-bench is a Python harness that applies model-generated patches to
real GitHub repos in Docker. We don't reimplement it; we ADAPT it:
- `evaluations/swebench-adapter.py` — reads a SWE-bench instance JSON
  (`{repo, base_commit, problem_statement, test_patch, FAIL_TO_PASS, PASS_TO_PASS}`)
  and emits an AIECP scenario YAML that drives `bug-report` workflow
  against the SWE-bench repo state
- `evaluations/scenarios/swebench-*.yaml` — generated scenarios (not
  committed; generated on-demand by the adapter)

### Realistic scope — harness stub this phase
Full SWE-bench eval needs Docker (blocked on Item 3). This phase:
- ADR-0031 records the integration design
- `evaluations/swebench-adapter.py` — the adapter (works on the JSON
  format; doesn't need Docker to convert instances to scenarios)
- 1 sample instance committed (`evaluations/swebench-samples/sympy-1.json`)
- `executor/examples/e2e-swebench-adapter/drive-run.mjs` — proves the
  adapter converts a SWE-bench instance to a valid AIECP scenario

## Item 5 — Adaptive Workflow Routing (Risk-Based Fast-Path)

### Problem
A 1-line typo fix runs the full 8-state bug-report FSM. Pro-LLM:
"Basit tip düzeltmelerinde hızlı-yol (Fast-Path), mimari değişikliklerde
ise tam anayasal FSM devreye girmelidir."

### Design
`executor/src/risk-classifier.ts` classifies a request as
`trivial | low | medium | high | critical`:
- `trivial` (1-line typo, doc-only): **fast-path** — skip FSM, emit
  a single `Decision(what: "fast_path_applied")` + apply + verify
- `low` (small bug fix, <50 LOC changed): full FSM but reduced
  question budget (0 instead of 1)
- `medium` (feature, 50-500 LOC): full FSM (current default)
- `high` (architectural, 500+ LOC): full FSM + mandatory `code-review` after
- `critical` (security, prod data): full FSM + `human-approval-required`
  gate (new transition that blocks until `aiecp:confirm gate: human`)

### Signals (pro-LLM's "risk and complexity")
- Diff size (LOC) — from `git diff --stat`
- File types touched (`.md`-only = trivial; `.ts` + test = low; core
  module = high; auth/security = critical)
- Number of files changed (1 = trivial; 2-5 = low; 6-20 = medium; 20+ = high)
- Keywords in request ("security", "auth", "password", "payment" → critical)
- Existing known-failure memory match (regression risk → at least medium)

### File layout
- `executor/src/risk-classifier.ts` — the classifier (pure function, no I/O)
- `workflows/_router.md` — new "Fast-Path" section explaining when trivial
  skips the FSM
- `executor/examples/e2e-risk-classifier/drive-run.mjs` — regression test
  (5 risk levels × 2 scenarios each = 10 assertions)

### What does NOT change
- The FSM definitions in `.sm.yaml` — unchanged. The risk classifier
  is an outer router that decides WHETHER to enter the FSM or take
  the fast-path. This keeps the FSM purity (every workflow still has
  the same states) while adding a practical escape hatch for trivial work.

## Phase 3 — Production Hardening (Sandbox + SWE-bench Pass@1)

> Pro-LLM'in nihai tavsiyesi: "Phase 3'e geçerken tek odak noktanız
> SWE-bench adaptörünü 10 gerçek Python/TS issue'su üzerinde koşturup
> ilk somut başarı skorunu (Pass@1) belgelemek ve Docker sandbox
> çalıştırıcısını run.ts içine bağlamak olmalıdır."

### Hedef 1 — Docker Sandbox Çalıştırıcısı

**Durum**: ADR-0030'da karar kayıtlı, stub yok. Bu fazda gerçek
implementasyon.

**Dosyalar**:
- `executor/src/sandbox-runner.ts` — Docker daemon varsa container'da
  komut çalıştırır; yoksa `execSync`'e fallback yapar (development mode,
  clear WARNING ile). Asla sessizce unsafe moda düşmez.
- `sandbox/Dockerfile.aiecp-executor` — minimal image: node:20-alpine +
  python3 + git. `--read-only` rootfs, `--cap-drop=ALL`, no network.
- `sandbox/run-in-sandbox.mjs` — CLI wrapper.

**run.ts entegrasyonu**: `execute-workflow` state'inde sandbox-runner
çağrılacak — child workflow'un komutları container içinde çalışacak.
Bu opsiyonel: `WorkflowRunOptions.sandbox: true` ile aktive edilir.

**Test**: `executor/examples/e2e-sandbox/drive-run.mjs` — Docker yoksa
fallback modunu test eder; Docker varsa real container run yapar.

### Hedef 2 — SWE-bench Adapter + Pass@1

**Durum**: ADR-0031'de tasarım kayıtlı, adapter yok. Bu fazda gerçek
implementasyon.

**Dosyalar**:
- `evaluations/swebench-adapter.py` — SWE-bench instance JSON'ı okur,
  AIECP scenario YAML'ye çevirir. ~200 satır Python.
- `evaluations/swebench-samples/` — 1-3 gerçek SWE-bench instance
  (MIT lisanslı, küçük — sadece metadata, repo state değil).
- `executor/examples/e2e-swebench-adapter/drive-run.mjs` — adapter'ın
  instance → scenario dönüşümünü kanıtlar.

**Pass@1 hedefi**: Pro model "10 issue'da en az 1 başarı" dedi. Bu
fazda adapter'ın çalıştığını + 1 örnek instance'ın doğru scenario'ya
dönüştüğünü kanıtlıyoruz. Gerçek 10-issue run Docker gerekir (Hedef 1'e
bağımlı) — bu fazda Docker varsa koştururuz, yoksa simulated.

### Phase 3 Test Budget
- 2 new e2e drivers (sandbox, swebench-adapter)
- Target: ~30 new assertions, total 1265 → ~1295
