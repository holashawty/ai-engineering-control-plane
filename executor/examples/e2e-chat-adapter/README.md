# End-to-end proof: chat LLM adapter + chat-output validator

**This is the proof point that closes the "chat LLM support" gap.**
The repo's previous adapters (`claude-code`, `codex`) targeted CLI
tools with tool use. A chat LLM (ChatGPT, Claude chat, Gemini chat,
GLM chat, etc.) has *no* tool use — only text in, text out. This
proof demonstrates that such an LLM can still drive the full AIECP
framework by emitting structured evidence as fenced code blocks
(`aiecp:evidence`, `aiecp:memory`, `aiecp:advance`, `aiecp:question`)
in its text response, and that the validator script correctly parses
+ schema-validates those blocks.

## What this run is, and what it isn't

**Is:** a structural proof of the chat protocol + validator pair. The
simulated chat LLM response in the driver is realistic (modeled on
what a chat LLM following `CHAT-ENTRYPOINT.md` would produce for a
"login sometimes fails" report), but it is scripted, not generated by
a live LLM. The validator's parsing and schema-validation logic is
real — it uses the same `ajv` + Phase 1 schemas as the executor's own
`EvidenceStore`.

**Isn't:** a recording of a real ChatGPT/Claude chat/Gemini chat
session emitting blocks in this format. That requires a live
multi-turn session with a real chat LLM — a separate milestone,
honestly out of scope for this proof. The protocol is documented
in `CHAT-ENTRYPOINT.md` and the validator works against any text
that follows the protocol; whether a real chat LLM follows the
protocol is the open question.

## What the run proves (32 assertions, all passing)

1. **Chat adapter capabilities are honestly declared.** Every
   capability is `false` — no tool use, no filesystem, no shell, no
   test runner, no native skills, no browser, no MCP. Pretending
   otherwise would let the executor believe the agent can do things
   it cannot, violating `constitution/constitution.md` §3
   ("autonomy is bounded, not implicit").

2. **`renderEntrypoint` produces `CHAT-ENTRYPOINT.md`.** Idempotent
   (byte-identical on repeat run, per ADR-0006). The generated
   content includes the 30-second orientation, all skill names +
   descriptions, the evidence protocol examples, and the explicit
   note that `Validation.method` for chat LLMs is `"manual_review"`
   (mental simulation), never `"app_validation"` (would require
   running code).

3. **`translateObservation` is a no-op that throws.** Chat LLMs emit
   `Event`s directly as text per the protocol; they don't have raw
   tool observations to normalize. Calling `translateObservation` on
   the chat adapter is a programming error in the caller — the
   adapter throws rather than silently producing garbage.

4. **Validator accepts well-formed responses.** A simulated 11-block
   response (1 trace, 2 events, 1 decision, 1 expected, 1 actual, 1
   validation, 1 memory, 2 advances, 1 question) is parsed and
   schema-validated — all 11 blocks pass.

5. **Validator rejects malformed blocks.** Five separate defects are
   caught: unknown evidence kind, missing required fields, bad id
   pattern (must match `^<kind>-[a-zA-Z0-9_-]+$`), bad YAML. Each
   produces a clear error message identifying the block and the
   specific schema violation.

6. **Validator rejects input with no AIECP blocks at all.** Pure prose
   is rejected with a clear "no aiecp:* blocks found" message.

7. **Validator supports stdin input.** A chat LLM response can be
   piped directly: `cat response.md | node scripts/validate-chat-output.mjs`.

8. **Protocol coverage is complete.** The simulated response
   exercises all 4 block kinds (`evidence`, `memory`, `advance`,
   `question`) and 6 distinct evidence kinds (`trace`, `event`,
   `decision`, `expected`, `actual`, `validation`). This proves the
   protocol is expressive enough for a full bug-report workflow run.

## How a chat LLM uses this (worked example)

A user uploads this repo's zip to ChatGPT/Claude chat/Gemini chat and
says: *"Our login endpoint sometimes returns 500, the logs show
something about a token refresh race condition."*

The chat LLM:

1. Reads `CHAT-ENTRYPOINT.md` first (per its instructions).
2. Reads `workflows/_router.md` → identifies `bug-report` workflow.
3. Reads `workflows/bug-report.sm.yaml` → walks states.
4. Asks the user to paste `src/auth/login.ts` and the log line.
5. Emits evidence as fenced code blocks in its response:

   ````
   ```aiecp:evidence
   kind: trace
   data:
     id: trace-locate-1
     started_at: 2026-08-14T10:32:00Z
     event_refs:
       - event-log-line
   ```
   ````

6. The user (or a future agent) extracts these blocks and runs:

   ```bash
   node scripts/validate-chat-output.mjs path/to/chat-response.md
   ```

   This validates each block against `evidence/schema/*.schema.json`
   and `memory/schemas/*.schema.json`. Schema-valid blocks can then
   be replayed through the real executor's `WorkflowRun` API by a
   tool-using agent (or future script).

7. The chat LLM honestly notes: *"My `Validation.method` is
   `manual_review` (mental simulation). A tool-using agent should
   re-run this verification later to flip the method to
   `app_validation` and apply the actual fix."*

## Why this matters

Before this proof, the repo's claim that "any cloud/local/chat LLM
can use this framework" was an architectural assertion without a
concrete demonstration. The CLI adapters (`claude-code`, `codex`)
only covered tools with native tool use — a tiny fraction of the
LLM landscape. This proof closes that gap: any chat LLM that can
read text and produce text can now drive the framework, by following
the protocol in `CHAT-ENTRYPOINT.md` and emitting structured blocks
that the validator can check.

The honest remaining gap: whether a real chat LLM *actually* emits
blocks in this format when given the entrypoint. That's a live-session
test, not a structural proof. The protocol + validator pair is ready;
the live LLM session is the next milestone.
